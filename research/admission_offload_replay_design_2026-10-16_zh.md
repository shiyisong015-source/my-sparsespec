# SparseSpec 动态准入、CPU 冷 KV 淘汰与完整重放恢复设计

日期：2026-10-16。讨论基准：`fca9953`，分支 `research/sparsespec-reproduction`。

本文记录用户已经确认的方向，供逐文件实现与检查使用。主体保留设计和验收要求；**实际实现范围与验证状态见第 12 节**，不能将所有建议都视为已实现。

现有 2026-10-14 交接文档用于追溯旧版本；关于准入、CPU 缓存和重放的下一版要求，以本文记录的最新决定为准。

## 1. 已确认的设计

1. 允许多个请求同时处于 prefill，去掉“已有一个 NORMAL 就不再准入”的限制。
2. 沿用 vLLM 的全局 token 预算概念，参数采用 `max_num_batched_tokens`。Prefill、重放、Draft 和 Verify 共用每轮预算。
3. `chunk_size` 保留为单请求每轮 prefill／重放的上限；调度器给出每请求本轮实际 token 数，输入准备严格执行这个计划。
4. 新请求按实际占用、即将执行的操作及必要工作空间准入，不再为所有请求的最大输出长度同时预约 GPU／CPU KV。
5. KV pool 和其他缓冲额度先确定，再按留给中间结果的显存容量，标定安全的全局 token 预算；运行时用它限制 forward 大小。首版不要求动态伸缩 KV pool。
6. CPU 冷 KV 是可淘汰缓存。CPU 容量不足时按 LRU 淘汰，之后通过完整重放恢复；首版不实现掩码补齐冷 KV。
7. CPU 达到容量水位后暂停新请求开始 prefill。已经开始的请求与恢复所需的重放仍需有推进机会，不能把它们一起禁止。
8. 淘汰 CPU 冷 KV 不必立即释放 GPU 热 KV。只要热 KV 有效，请求仍可继续 Draft。
9. 恢复采用完整重放，但**保留未验证草稿 token、原始草稿概率和实际草稿长度**。释放 KV 不等于丢弃推测状态。
10. 纯重放使用已确定的 token，只重建 KV，不采样、不覆盖原始草稿概率、不重复增加输出 token 数，也不重置输出预算。
11. 多 prefill 和恢复／重放空间不足时，先参考 vLLM 的请求抢占机制：暂停其他请求、安全释放其 KV、保留 token 历史，后续按需重算。Self-spec 还要保留未验证草稿和原概率。
12. 允许在达到配置的 Draft 长度上限之前结束本轮 Draft。首版可以按已经积累的实际 Draft 长度选择进入 Verify 的请求，随后根据冷 KV 所在位置直接验证、恢复或重放。具体触发阈值和排序仍需确定。

当前保持配置的 Draft 长度上限和 r；允许本轮实际 Draft 长度提前结束。自适应调整上限／r、传输预测、掩码重算和层间搬运优化不属于本次已敲定的实现要求。

**讨论收敛：** 暂停请求仍持有的概率等缓冲正常计入容量；元数据容量也是组 batch 的正常约束。这两项是实施条件，不单独称为调度策略缺陷。需要改进的是旧准入预约、多 prefill、抢占恢复，以及灵活结束 Draft 的机制。

## 2. 当前实现及已核实的问题

| CPU 异步流程延迟释放仍被 GPU 使用的资源 | `async_cpu_compact_scheduler.py` | 复用其完成事件保护，不能在改准入时绕过 |

### 为什么当前最多约 31 个请求

已运行配置：`r=.05`、`k=8`、总长度上限 32768，CPU 预算每 rank 为 1016087 页。

旧公式按每请求长度 `32768+8+1=32777` 估算，热 KV 为 1639 页，冷 KV 为 31138 页：

```text
(请求数 + 1) × 31138 <= 1016087
```

因此上限为 31。即使 CPU 实际没有冷 KV，这个预约仍限制 GPU 请求数。**31 是旧公式与实验配置共同产生的结果，不是模型或硬件必须的并发上限。**

## 3. 准入、组 batch 和存储状态分开管理

### 3.1 三个不同的数量

必须分别记录：

- 等待首次准入的请求数。
- 已经准入、仍持有状态／缓冲的请求数，包括等待 Verify、等待重放和暂停请求。
- 本轮实际参与 forward 的请求数和 token 数。

请求没有参与本轮计算，不意味着其草稿概率、索引、热 KV 已释放。不能通过把它移出 ready batch，就将这些资源从账面扣除。

### 3.2 每轮 token 计划

每请求本轮 query 数记为 `q_i`：

| 操作 | `q_i` |
|---|---|
| Prefill | `min(剩余输入, chunk_size, 可用 token 预算, 可分配 KV 页)` |
| 完整重放的前缀部分 | `min(重放剩余长度, chunk_size, 可用 token 预算, 可分配 KV 页)` |
| Draft | 通常为 1 |
| Verify | 实际草稿长度加 1；遵守当前验证窗口及 initial_idx 语义 |
| 等待传输、等待资源、STALL | 0 |

要求：

```text
sum(q_i) <= max_num_batched_tokens
```

Verify 窗口首版作为不可拆分操作，预算不足时延后；不能随意把它截短成 prefill chunk。配置必须能容纳至少一个合法 Verify 窗口，否则会永远无法执行。

调度计划必须同时被 GPU 页分配、token_ids 拼接、RoPE 位置、probability scatter、完成判断与异步输出对应关系使用。只在调度器中扣预算、输入准备仍按原 chunk_size 执行是不成立的。

### 3.3 调度优先关系

建议实现为：

1. 检查搬运及延迟释放事件，提交已完成事务，回收可用空间。
2. 推进已选定的恢复／重放／Verify；本轮释放资源时不能把其正在使用的 KV 当成可回收空间。
3. 为已有请求安排本轮计算；空间不足时通过卸载或请求抢占腾空间，抢占后保留可恢复状态。
4. 在资源与 CPU 水位允许时准入新的 prefill。

这是先保证已有请求推进的原则，不要求首版引入复杂收益预测。多个候选之间的公平策略仍需具体确定。

### 3.4 提前结束 Draft 与请求抢占

两者可以配合，但作用不同：

- 请求抢占：暂停请求并回收其 KV，保留历史和草稿，后续恢复／重算；直接承担腾空间的职责。
- 提前结束 Draft：固定本轮已有的 m 个草稿，不再为本轮追加新草稿，将请求转入待 Verify；本身不保证释放显存。

根据存储状态选择后续路径：

| 准备验证的请求 | 下一步 |
|---|---|
| 全量 KV 已在 GPU | 对实际 m 个草稿直接 Verify |
| 冷 KV 在 CPU | 获得 GPU 空间后恢复，再 Verify |
| 冷 KV 已淘汰 | 保留原草稿和概率，重放前缀，再 Verify |

即使直接 Verify 完成，当前实现也默认保留全量 GPU KV。若目的是腾空间，需要明确安排后续冷热重排／卸载或请求抢占，不能把 Verify 完成等同于自动释放冷 KV。

当前输入准备和状态断言仍依赖 `spec_stride` 与 `initial_idx` 推导窗口。实现提前 Verify 时必须显式对齐实际草稿长度 m、m+1 个 query、概率行和 tail 回收；仅修改 status 不够。m=0 不能直接进入当前要求有草稿的 rejection 路径，应继续获得首个草稿或走明确的普通生成路径。

## 4. 固定 KV 与其他缓冲后，用中间结果容量约束 forward

### 4.1 已确认的容量划分

以每个 TP rank 为单位：

```text
中间结果可用额度
  = 进程显存预算
  - 模型权重
  - 固定 KV pool
  - 已确定的其他缓冲额度
  - 安全余量
```

“其他缓冲额度”需要明确包含请求持久缓冲、logits／采样／rejection 的约定上界、Graph 保留资源、attention 工作区以及异步期间必要的共存缓冲。已包含的空间不能再重复扣除。

临时张量与 Attention／MLP 中间结果通常由同一个 PyTorch CUDA 分配器管理，可以复用生命周期不重叠的存储。**不能把各张量各自的最大值简单相加，作为真实峰值。** Graph 和异步事件会限制复用时机，应按实际生命周期标定。

KV pool 是启动时申请的大张量。pool 中的空闲页仍属于它，不会自动成为 MLP／采样张量的可分配空间。本设计不依赖动态借用这些空闲页。

### 4.2 标定和运行约束

1. 固定模型、TP、dtype、KV pool、请求上限、k/r 和其他缓冲预算。
2. 用预算内的多 prefill、Draft/Verify 混合及重放情形，标定输入 token 数与实际显存峰值的关系。
3. 覆盖真实 CPU 异步流水线：上一轮输出仍被消费时，下一轮已经在计算。
4. 覆盖 Graph padding 后的真实形状。`实际 N <= 预算` 不等于 padding 后 `N_hat` 也能安全容纳。
5. 取各 TP rank 可支持范围的交集，加安全余量，确定全局 token 上限。
6. 在验证过的配置范围内按该上限组 batch；k、请求上限、Graph 桶或其他缓冲策略变更后重新检查。

这里的目标是给已校准配置提供可执行的容量约束，不是依赖发生 OOM 后缩 batch。PyTorch 按需分配本身不会自动调整 batch。

### 4.3 当前非 KV 缓冲事实，供标定使用

Qwen3-8B 的词表大小为 151936，以下形状为每个 rank：

| 缓冲 | 当前形状／类型 | 生命周期 |
|---|---|---|
| 每请求草稿概率 | `[10,V]`，FP32，约 5.80 MiB | 已准入期间持有；释放 KV 不得一并丢失 |
| 每请求选择索引 | `[36,4,6144]`，int32，约 3.38 MiB | Compact 指针持有；随旧指针安全释放 |
| 完整 logits | `[N_hat,V]`，FP16 | LM head 后 TP all-gather，每个 rank 均有完整结果；Graph 结果可能常驻 |
| 采样随机工作区 | `[N_hat,V]`，FP32 | 按本轮采样形状申请 |
| 采样概率 | `[N_hat,V]`，FP32 | 需要保留给 Draft scatter／Verify；异步可跨轮共存 |
| Rejection 收集矩阵 | 两份 `[D,V]`，FP32 | `D` 是本次实际验证的草稿总数；从原始概率再次复制 |
| Rejection 恢复采样随机区 | `[B_verify,V]`，FP32 | 本次 rejection 内使用 |

上述临时缓冲目前主要按形状 `torch.empty` 申请，由缓存分配器复用。首版不要求实现概率专用分配器。纯重放禁止采样；跳过纯重放／无用 prefill 位置的词表投影属于明确的优化机会，但需要单独适配输出行与 Graph，不得假定已经支持。

## 5. GPU 空间检查与请求抢占

### 5.1 按操作检查真实峰值

| 操作 | 必须有的资源 |
|---|---|
| 新 prefill／继续 prefill | 本轮追加页、请求缓冲额度、必要推进空间 |
| Draft | 本轮追加页及相关元数据空间 |
| Resident 冷热重排／卸载 | 旧源页继续保留时的新热 KV 目的页，加 CPU 新冷 KV 空间 |
| 从 CPU 恢复 | 全部缺失冷 KV 的 GPU 目的页、随后的 Verify 追加空间 |
| 完整重放恢复 | 重放中累积建立的完整前缀 KV，加完整验证窗口及必要工作空间 |

重排不是每个 prefill chunk 都执行。当前首次 prefill 后的首轮 Draft 使用全量上下文，首次 Verify 才产生稀疏选择；有压力时才物理重排。其他请求处于 prefill 时，也可能需要为已有 Draft/Verify 请求进行重排。

### 5.2 优先参考 vLLM 的抢占与恢复机制

仅检查“下一个 chunk 放得下”不能保证已有请求最终能恢复、完成 Verify。

本地 vLLM 0.11 的 `vllm/v1/core/sched/scheduler.py` 在当前请求申请 KV block 失败时，选择受害请求、释放其 KV、将其状态设为 PREEMPTED、重置已计算进度并放回等待队列；token 历史保留供后续重算。下一版可以沿用这个调度框架，无需先实现一套按所有请求最终输出长度预约空间的机制。

建议流程：

1. 为选定请求计算下一步所需的真实 KV 空间。
2. 空间不足时选择其他可抢占请求，在相关事件完成后释放其 KV。
3. 保留被抢占请求的 token 历史；有草稿的还要保留实际草稿长度和原概率，记录待重放状态。
4. 重试分配；本轮调度和后续等待顺序应避免刚腾出的空间又立即被新准入抢走，或同一个恢复对象反复被抢占。
5. 对选定的待验证请求，可按实际 Draft 长度提前停止 Draft，然后完成必要的恢复／重放和 Verify。

抢占的是调度中的请求执行资格和可回收 KV，不是强行中断正在运行的 CUDA kernel。真正回收仍需遵守异步计算、传输和控制事件。

**多个尚未完成的 prefill 是抢占机制必须覆盖的情况。** 它们还没有产生可用于当前冷热卸载路径的选择结果；当前 `_pressure_victim()` 只处理 resident compact 请求。如果多个长输入轮流追加 KV，把 pool 填满，却没有一个完成首次 prefill／Draft／Verify，现有卸载路径无法救场。全局 token 预算只约束本轮增量，不约束历轮积累。

因此，多 prefill 场景要支持抢占尚未完成 prefill 的请求：保留原始输入和有效生成状态，安全释放 FullCachePtr 的 KV，之后按 chunk 重算／继续 prefill。它与已有草稿请求的恢复路径要区分；不能假定当前 `_pressure_victim()` 已覆盖这个能力。不要求退回“永远只允许一个 prefill”。

目前先以请求抢占、已有工作优先和明确的候选顺序保证推进。是否再引入跨轮空间预约、最小保留配额等更复杂机制，留待实现与压力测试后判断。

实际实现应区分：

- 已提交搬运、计算和延迟释放仍占有的空间。
- 确认完成后可以回收的空间。
- 拟回收但尚未回收的空间。

第三类可以用于规划，但不能在真正分配之前就当成空闲页。

若单个请求的完整验证所需 KV 和必要工作空间即使独占也无法容纳，属于当前计算路径的不可运行配置。LRU、chunk prefill 和重放都不能消除 Verify 需要完整 KV 的事实，需要在适当边界明确处理，不能无限等待。

## 6. CPU LRU 缓存与容量水位

### 6.1 LRU 管理对象

首版建议按请求的完整 CPU 冷 KV 副本管理，保持现有搬运粒度。LRU 最近使用时间由副本创建和恢复使用更新；仅执行 GPU 热 KV Draft 不视为访问 CPU 副本。

这与“从哪些 GPU 请求卸载冷 KV”是两个不同的选择：

- GPU 卸载：为了释放 GPU 空间，选择可搬运请求。
- CPU LRU：为了容纳新 CPU 冷 KV，选择可淘汰 CPU 副本。

用户已明确选择后者允许丢弃 CPU 数据、以后重计算；不是只给 GPU 卸载策略换一个 LRU 排序。

### 6.2 淘汰规则

- 只淘汰当前未被搬运使用、能够安全删除的 CPU 副本。
- 正在 D2H 写入、H2D 读取、仍被异步引用的副本不可提前回收。
- 删除 CPU 副本后显式设置“冷 KV 缺失”，不能把 `cold_count==0` 误解为逻辑上没有冷 KV。
- 热 KV 完整时可以继续 Draft；执行 Verify 前必须恢复或重计算。
- 所有 TP rank 使用一致的候选身份、淘汰顺序和状态转换。数据真正可回收的条件包含各 rank 完成状态。
- 有效 CPU payload 页预算、待完成事务和延迟释放都要计数。清除 Python 引用不一定立即降低 pinned allocator 的缓存占用；容量标定应同时观察主机实际内存。

### 6.3 水位控制

达到 CPU 高水位时停止新请求开始 prefill，已有请求的恢复／重放仍可按预算推进。建议采用高、低水位避免频繁开关；**具体阈值尚未确认，不能自行写成已决定的默认值。**

LRU 删除数据释放的是存储容量，后续会产生重算成本，不能用无限新准入抵消水位控制。LRU 也不保证没有重算抖动，仍需上一节的抢占／恢复调度顺序。

## 7. 完整重放恢复：草稿和概率必须保留

### 7.1 状态与边界

执行状态和 KV 存储状态应分开表达。建议至少能区分：

| KV 存储状态 | Draft | Verify |
|---|---|---|
| 全量在 GPU | 可以 | 可以 |
| 热 KV 在 GPU，冷 KV 在 CPU | 可以 | 等待恢复 |
| 热 KV 在 GPU，冷 KV 已淘汰 | 可以 | 等待重放 |
| KV 已安全释放，等待／正在重放 | 暂停 | 重放完成后验证原草稿 |

恢复进度不能借用 `len_input`。该字段是原始 prompt 长度，现有 `prefilled` 又依赖 token 历史长度；已有输出的请求直接改成 NORMAL，会有提前结束重放、错误生成 token 的风险。需要独立记录已确认前缀边界、重放目标、游标和阶段。

### 7.2 必须保留的请求信息

- 原始 prompt 与原输出长度上限。
- 已确认的 token 历史及其结束边界，包括尚未作为下一轮输入处理的最新确认 token。
- 已产生的未验证草稿 token、原始完整草稿概率、实际草稿长度。
- 原始 request_id、sample_id 对应关系和累计接受率统计；暂停恢复不得当成新请求重复计数。
- 有效的异步完成／消费事件；清理旧阶段 metadata 时不能破坏上一轮尚未完成的输出处理。

### 7.3 恢复过程

1. CPU 淘汰时仅标记冷 KV 缺失；热 KV 可继续用于 Draft。
2. 按实际 Draft 长度决定进入 Verify，或请求被抢占而必须释放 GPU KV 时，停止为它提交新的 Draft。
3. 消费该请求已经提交的异步结果，落实真实 token 与对应概率，处理占位 token 和 VERIFY→STALL 的未完成结果。
4. 固定已确认前缀和本轮草稿快照；保留概率缓冲引用。
5. 等相关 GPU／控制操作不再使用旧 KV 后，释放旧页与旧选择索引；这是暂停恢复，不是整个请求完成／retire。
6. 调度到该请求并取得必要空间后，分 chunk teacher forcing 重放验证窗口之前的前缀。
7. 对保留的原草稿执行完整 Verify，使用其原始概率作 draft 分布；此时产生目标概率。
8. Rejection 确认输出、截断无效 KV，选择下一轮热 KV，继续 Draft。

**不丢弃草稿，不重新采样已确定的 token，不把重放计算计入新输出 token，不重置原输出预算。**

### 7.4 验证窗口与 KV 分配

设已确认序列为 `c[0:L]`，草稿为 `d[0:m]`。按照通常的 next-token 验证语义：

```text
纯重放前缀：c[0:L-1]
验证窗口：  [c[L-1], d[0], ..., d[m-1]]
```

验证窗口共 `m+1` 个输入位置，为每个草稿产生目标概率及最后的 bonus 候选。具体索引必须与当前 `initial_idx`、异步输出和概率对齐方式核验。

**当前原生 Verify 只追加 1 个 KV 槽位，是因为前面的草稿 KV 原本已存在。完整释放后，这个前提失效。** 新路径要为整个验证窗口追加需要的页，而不是仍追加 1 页。保持因果位置、RoPE 和概率行对应正确。

不能将重放期间重新计算出的目标概率写回原 `draft_probs`。Rejection 必须比较原提议分布与新计算的目标分布。采样器中的随机工作区变量 `q` 与数学上的 draft 分布也不是同一个对象。

### 7.5 当前未证明的部分

本设计需要新的正确性检查。旧交接已有完整前缀重算严格数值对照失败记录，不能将本文视作解决了旧数值问题。优先确认输入历史、窗口、KV 内容和位置语义；浮点累加与 TopK tie 导致的轨迹差异应单独解释，不用逐位一致代替所有验收标准，也不以数值误差为由忽略索引和状态错误。

## 8. 仍需保留的硬约束

本节与已暂停请求的持久缓冲计数都属于正常容量管理，不单独列为准入设计缺陷。

## 13. 压力测试后的恢复准入修正（2026-10-16）

首版吞吐对照见 `log/dynamic-compact-perf-20261016/report_zh.md`：
同序 128 条 LCB、输出上限 2048，CPU 配额 40000 页时为旧版的 2.513 倍，
CPU 充足时提升约 5.28%。GPU pool 65536 页时，新版运行 505.76 秒仅完成
59/128，保留证据后主动终止；旧版 430.77 秒完成全部请求。
首版恢复候选绑定整个未完成集合的最小 request_id，造成后段逐请求生成。

用户确认参考安装环境中的 vLLM 0.11.0 V1 抢占／恢复机制，按以下规则修正：

1. `running` 与等待恢复分开。需要完整重放但尚未重新准入的请求进入
   `_waiting_replays`；需要 CPU 冷 KV 的 Verify 也作为等待恢复候选。
2. 运行集合先使用本轮预算，包括已经开始的部分重放。按 request_id 保持优先顺序，
   较晚请求不能为自己的下一块抢占较早请求。
3. 本轮提出抢占后，不再准入等待恢复或新的 prefill；原有异步结果仍先消费，
   旧 KV 仍通过 retirement 事件安全释放。
4. 本轮无抢占时，用剩余 token／实际空闲 KV／元数据容量依次检查恢复候选。
   首块重放准入后转入运行集合，不再等前一请求整段输出结束。
5. 借鉴 vLLM 的队列和预算顺序，同时保留我们的额外容量保护：检查已知输入／
   重放前缀、保留草稿验证窗口及重排工作空间能否推进。
   这不按最大输出长度预约；仅按首个 chunk 的空间准入会使长前缀反复重建。
6. 等待恢复不通过抢占正在计算的请求获得准入；如所有请求都等待恢复、且没有
   可运行计算／传输／延迟释放可推进，则回收其他等待请求的 KV，保证至少一个恢复可执行。
7. CPU 冷副本仍有效时走传输恢复；冷副本缺失／请求完整 KV 被释放时走重放。
   不复制第三方 self-spec 分支中清空未验证草稿的处理，原草稿与概率继续保留。

参考源码：安装包 `vllm/v1/core/sched/scheduler.py` 的 running 分配、
抢占后 `waiting.prepend_request`、`if not preempted_reqs` 及 waiting 分配流程。
官方说明：https://docs.vllm.ai/en/v0.11.0/configuration/optimization.html 。

本次源码改动为 `dynamic_compact_scheduler.py`、`test_compact_native.py`；
README 和本文同步说明。
